The likely trigger when crossing into another chunk is therefore:

```text
Player crosses streaming boundary
-> required resident set changes
-> Engine calls synchronous ChunkSource::load()
-> one whole chunk pipeline runs on the main WASM/UI thread
-> rendering/input/event loop cannot run
-> visible freeze
```

The initial load may feel acceptable because it happens behind the loading overlay. Later section generation happens while the player is moving, so the same cost becomes a lock-up.

## Multithreading target

Move **only pure chunk construction** to workers first. Keep the game loop, WebGL, renderer resource ownership, player state, input, and chunk-store mutation on the main thread.

```text
Main thread
  StreamingPolicy decides required chunk keys
  -> enqueue (origin, LOD, seed, config, request generation)
  -> continue rendering current resident set
  <- receive completed ChunkPayload
  -> validate request is still wanted
  -> upload face/mesh/light GPU buffers
  -> install collision + chunk payload

Worker pool
  Generate architectural VoxelGrid with halo
  -> BFS voxel lighting
  -> build greedy surface mesh / face instances
  -> build SVO + serialize atlas data
  -> extract collision AABBs
  -> post ChunkPayload back
```

This split is clean because `LocalChunkSource::load()` already encapsulates exactly those pure operations, and its output is a self-contained `ChunkPayload`. ## Worker constraints

WebAssembly threads with shared memory require cross-origin isolation in browsers, typically `Cross-Origin-Opener-Policy: same-origin` plus `Cross-Origin-Embedder-Policy: require-corp`. If you do not want to impose that immediately, use ordinary Web Workers with a second WASM instance and transfer completed typed-array payloads back; it will still remove the visible UI freeze, though payload transfer/allocation overhead must be measured.

Do **not** share a WebGL context with generation workers. WebGL buffer and texture creation should remain on the render thread; workers should output plain serialized chunk data.

## Correct lighting rule

Every non-emissive surface should follow this rule:

\[
\text{final surface color} =
\text{wall albedo} \times
(\text{indirect light} + \text{direct flashlight/light contribution})
\]

Not this:

\[
\text{final surface color} =
\text{indirectly colored wall} + \text{white flashlight replacement}
\]

In shader terms, make the material color the immutable base:

```glsl
vec3 albedo = materialColor(aFaceMeta.w); // wall -> vec3(0.867, 0.800, 0.400)

vec3 indirect = sampleLightVolume(faceCenter) * aoTerm;
vec3 direct = flashlightTerm + selectedFixtureTerms;
vec3 lighting = max(indirect, vec3(0.04)) + direct;

// Preserve material hue under all direct illumination.
vec3 lit = albedo * lighting;

// Only emissive fixtures bypass ordinary albedo lighting.
if (isEmissive) {
    lit = max(lit, emissiveFixtureColor);
}
```

The flashlight should make the walls become **brighter yellow**, perhaps slightly desaturated at extreme brightness after tone mapping, but never neutral grey.

## Lighting restoration order

1. Render `materialColor` only—no fog, lights, AO, or shadow—and verify walls are unmistakably `0xddcc66`.
2. Add baked light-volume RGB multiplied by albedo; verify dark walls remain yellow-brown rather than grey.
3. Add AO and face-direction bands.
4. Add flashlight alone; verify it brightens yellow, not replaces it.
5. Add fixture lights.
6. Add hero shadow.
7. Add fog last.

This isolates the exact pass that destroys the wall color instead of tuning all lighting at once.
